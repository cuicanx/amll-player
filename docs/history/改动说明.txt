 AMLL Player 定制版（cuicanx 维护）  改动说明
================================================================

一、这一版做了什么
----------------------------------------------------------------
  1. 品牌：把我（cuicanx）设为项目的主要维护者与贡献者。
  2. F11 无边框全屏：默认关闭，在「设置 → 常规」里打开后才生效。
  3. 长歌曲列表：快速连续滑动不再"加载跟不上"，卡片逐个渐入。
  4. 所有浮层统一成与「青柠起始页」同款的毛玻璃。
  5. 自动更新模块修复：主更新源改成我的仓库，并解决"下完装不上、
     反复卡在同一步"的问题。
  6. 安装程序改为全程中文。
  7. 云端构建提速。

三、F11 无边框全屏
----------------------------------------------------------------
  - 默认关闭。关闭状态下按 F11 完全没反应，不会抢占按键。
  - 打开路径：设置 → 常规 → 「启用 F11 无边框全屏」。
  - 打开后按 F11 进入 / 退出；退出时会把自绘标题栏、它的高度变量、
    最大化按钮图标一起恢复，不会出现"退出全屏后顶部错位"。
  - 右键菜单里的「全屏 / 取消全屏」和 F11 走同一套逻辑，
    两边状态不会打架。
  - 关闭这个开关时，如果当前正处于全屏，会自动退出全屏。


四、长列表：加载为什么跟不上，怎么改的
----------------------------------------------------------------
  以前的毛病：列表里每出现一行，就单独向后端要一次这首歌的数据。
  快速连续往下滑时，一屏十几行 = 十几个请求同时排队，而且是"你先到
  你先办"。你滑到第 500 首时，请求还在处理第 300 首，所以看到一片
  骨架屏（灰块），过一会儿才陆续出来。

  改法：
  - 同一瞬间的所有请求合并成"一次批量查询"（每批 80 首）。
    十几行 = 1 次请求，而不是十几次。
  - 已经在队列里的同一首歌不会重复请求；行滑出屏幕就立刻退出队列，
    不再占用后面的请求名额。
  - 滚动过程中每 120ms、以及停下来 90ms 后，都会把"可视区域上下各
    几屏"的歌提前取好放进内存。等你滑过去时数据已经在了，直接显示。
  - 歌曲数据变更（导入/编辑）时先保留旧内容、后台刷新，不会整列变灰。
  - 卡片高度固定 68px，数据到达时不会因为高度变化导致列表重新测量。

  卡片渐入：
  - 卡片进入视口时轻轻淡入并上移 6~8px，用时 0.26 秒；
  - 按行号错开 0/26/52…ms（最多 130ms），形成"一个接一个"的观感；
  - 往上滑和往下滑的起始方向相反，看起来更自然；
  - 只动透明度和位移（不触发重排），动画期间照常可以点击；
  - 系统开启"减少动态效果"时自动关闭。


五、浮层毛玻璃（对齐起始页）
----------------------------------------------------------------
  从起始页的 CSS 里取到的原始配方：
    backdrop-filter: blur(30px) saturate(1.25)
    半透明底色 + 1px 极淡描边 + 柔和大阴影 + 0.25s 过渡

  已统一覆盖：提示框（toast）、右键菜单、三点菜单、下拉菜单、
  弹出面板、对话框、录音面板、当前播放列表浮层。
  同时删掉了之前的几套一次性材质（blur(24px)、blur(5vh) brightness、
  纯黑 #2228 内层），避免同屏出现两种玻璃。

  透明度按白天/暗夜分别调过，保证文字可读；模糊半径、描边、圆角、
  阴影层次完全一致。


六、自动更新：失败到底出在哪
----------------------------------------------------------------
  主更新源：https://github.com/cuicanx/amll-player
  （仓库地址在 README、Cargo.toml、构建流水线里都有记录，不需要额外
   补充。tauri.conf.json 里原本写的是上游 amll-dev 的地址，已改。）

  配置为「镜像优先、GitHub 直连兜底」：
    1) https://gh-proxy.com/https://github.com/cuicanx/.../latest.json
    2) https://github.com/cuicanx/.../latest.json
  镜像不可用时会自动尝试下一个，不会因为单一镜像挂掉就永远更新不了。

  以下是这次定位到的 5 个真实失败原因：

  (1) 签名公钥不匹配（最致命）
      tauri.conf.json 里的 pubkey 是上游 amll-dev 的公钥，但我们的包是
      用本项目的私钥签的。结果：下载 100% 完成，到"校验签名"这一步
      必然失败。表现就是"下完了、提示安装了，但版本没变"。
      已改为本项目密钥对应的公钥（与 .signing/tauri.key.pub 完全一致，
      并在验证脚本里做了逐字节比对）。

  (2) 版本号根本没法比较
      以前版本号是 0.0.1+1137。semver 规定 "+" 后面是构建元数据，
      比较版本时会直接忽略。于是 0.0.1+1143 和 0.0.1+1137 被认为是
      "同一个版本"，更新检查形同虚设。
      已改为 0.0.1137 → 0.0.1143 这种把提交次数放进 patch 位的方案，
      版本真正单调递增。

  (3) 失败时没有任何兜底（"卡在同一步"的直接原因）
      原代码调用 downloadAndInstall 既没有 await，也没有 catch。
      一旦失败：按钮永远转圈、"正在下载"的提示永远不消失，只能重启
      应用；重启后再点，用的还是同一个已经坏掉的更新对象，于是继续
      失败 —— 这就是你遇到的"反复卡在同一环节"。
      现在：完整 try/catch/finally；失败会复位状态、关闭坏句柄、
      清空当前更新信息，下次点击会重新检查而不是重放旧错误。

  (4) 失败没有任何提示
      以前检查更新失败只写控制台。现在关于页会明确显示
      「更新失败：<原因>」，并给出「重试」「打开发布页」两个按钮；
      连续失败 2 次后会额外提示可以手动下载安装包。

  (5) 没有并发保护
      快速连点可能同时发起多个下载。现在用单例锁串行化，
      同一时间只允许一个下载/安装流程。

  上游更新提示（只提示，不参与更新）：
  - 额外查询 amll-dev 的预发布信息，只有确实比本机新时才显示一行
    小字：「上游有新构建（版本号），查看上游发布页」；
  - 这行字可点击，跳转到上游对应 Release 页面；
  - 查询失败、限流、断网都静默忽略，完全不影响主更新流程；
  - 它不会改变默认更新源，也不会触发安装。

  ⚠ 重要：这次必须手动装一次
  因为公钥从上游换成了本项目自己的，旧版本无法验证新包的签名。
  所以：请手动安装本次提供的安装包（覆盖安装即可，歌单和设置都保留）。
  从这一版开始，后续的自动更新才会正常工作。

八、构建提速
----------------------------------------------------------------
  只改 CI，不动本地生产构建配置：
  - CI 里把 release profile 覆盖为 thin LTO + 16 个 codegen units。
    （本地 Cargo.toml 仍是 codegen-units=1 + 全量 LTO，生产包不受影响）
  - Rust 缓存增加 cache-on-failure：构建失败或被取消时也保留缓存，
    下一次不用再冷编译一遍。
  预期：主要省在 LTO / 链接阶段。首次构建因为缓存键变化仍需全量编译，
  从第二次开始收益明显。实际耗时以云端记录为准（见安装说明）。
