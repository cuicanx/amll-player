================================================================
 第二轮性能优化：内存上限与后台 CPU
 约束：不改变画面、帧率、交互与功能，只减少无效工作
================================================================

一、先给结论：200MB 里有多少是"真占用"
----------------------------------------------------------------
  实测（不是估算）：

   歌词索引 index.bin       108,147,344 字节（约 103 MB）
                            mmap 只读映射，**惰性分页**
   你的音乐库               99 首歌，歌词合计 1,406,354 字符
                            ≈ 2.7 MB（平均 14,206 字符/首）
   WebView2 多进程基础      80~120 MB（渲染/GPU/网络/工具进程）
   前端堆 + 常驻 DOM/WebGL  30~50 MB
   Rust 主进程 + FFmpeg     20~40 MB

  三条判断：
  1) 103MB 的索引是**文件映射**，不是私有堆；系统内存紧张时可回收。
     它在任务管理器里显得大，但真实内存压力远小于这个数字。
  2) 你的库只有 2.7MB 歌词，所以"歌词缓存吃内存"在你这儿**不成立**。
     按 1000 首逐字歌词（YRC/TTML）估才有几十 MB。
  3) 因此本轮的价值不在"把 200 压到 120"，而在
     "别让它随着使用无限增长 + 后台别空转"。

二、本轮实际改了什么（8 项）
----------------------------------------------------------------
  M1. 歌曲缓存加上限（LRU 400）
      原先 song-batch-loader 的缓存是无上限 Map，每滑过一行就把带完整
      歌词的 Song 永久留下。现在超过 400 条淘汰最久未用的；滑回去时由
      预取兜底，实际不可见。
      收益：内存从"随滚动无限增长"变成"有天花板"。
      代价：无（极端回滚会多一次批量 IPC，被预取掩盖）。

  M2. 播放队列不再存歌词
      同一份歌词原先在 playList、originalList、shuffle 副本里各存一遍。
      入队时把 lyric / translatedLrc / romanLrc 清空，只留播放与显示字段。
      收益：队列内存降到约 1/3~1/4。
      代价：无（队列 UI 只用歌名/艺人/封面；歌词由播放器按需读取）。

  M3. 歌词解析不再把整份结果打进 console
      6 处 console.log 里有 5 处直接输出解析后的整份歌词对象；DevTools
      打开时这些对象会被额外持有。
      收益：调试时内存少几 MB，控制台也不再卡。
      代价：无。

  M4. 内存高压阀（仅紧张时释放全屏歌词页）
      JS 堆超过 400MB 且歌词页处于**关闭**状态时，才卸载该子树，
      回收 WebGL 上下文与整棵歌词 DOM（约 20~40MB）。
      正常使用不会触发（你的堆远低于 400MB），所以打开速度不变。
      代价：真正触发后，下一次进入全屏页会多一次初始化。
      这是你选择的"仅在内存紧张时释放"的实现方式。

  M5. FFT 循环加门控
      原先只在"歌词页打开"时启动，暂停播放或窗口最小化时仍以 60fps
      空转，每帧读 atom、算梯度、写 atom。现在要求
      「歌词页打开 && 正在播放 && 窗口可见」三者同时成立。
      收益：暂停时省掉一整条 60fps 循环；最小化时同理。
      代价：无（暂停时低频值本来就不该变化）。

  M6. 封面不再拉整个歌单
      歌单卡片只要 4 张封面，原实现却用 getByIds 取回整个歌单的
      完整 Song（含全部歌词）再筛。1000 首的歌单 = 一次几十 MB 的
      IPC 序列化 + 反序列化。
      新增 get_playlist_cover_paths，只 SELECT cover_path。
      收益：进首页/歌单时的 CPU 与瞬时内存尖峰明显下降。
      代价：无（多一个只读查询，SQL 走索引）。

  M7. 歌词索引路径集合改为磁盘缓存
      mmap 本身是惰性分页，真正的"全量读"发生在歌词同步时：
      为了拿到"已入库的文件路径集合"，会遍历整份 100MB+ 索引，
      把整个映射拉进工作集。
      现在结果缓存在 index.paths，按 index.bin 的 mtime 失效。
      收益：同步时不再全扫索引，工作集不因此上涨。
      代价：首次会生成一个几百 KB 的缓存文件。

  M8. 未改动搜索读取逻辑
      搜索结果仍需要遍历索引（没有倒排索引），改成流式读取会让搜索
      变慢。按你的约束"不牺牲流畅性"，这里保留原实现。

三、明确没做的（以及为什么）
----------------------------------------------------------------
  X1. 没有把 103MB 索引改成流式分块读取
      mmap 已经是按需分页；要降"任务管理器数字"只能主动 trim 工作集，
      而 Windows 上安全的做法收益不稳定、粗暴做法（清空整个进程工作集）
      会连音频缓冲一起踢掉，直接违反"不牺牲流畅性"。故只做了 M7。

  X2. 没有为降数字而关闭 WebGL 背景或降低歌词动画
      这是产品核心观感，属于你明确不允许牺牲的部分。

  X3. 没有强制 GC
     手动触发 GC 不可控，且会造成可感知的停顿。

  X4. 没有把主窗口的播放进度 atom 也停掉
      隐藏时停掉可以再省一点，但恢复瞬间需要重新对齐，有歌词跳动的
      风险。收益小于风险，不做。

四、后台/不可见状态的实际效果
----------------------------------------------------------------
  按你选择的"分级：主窗口冻结，任务栏照常"：
   - 主窗口不可见：低频 FFT 循环停止（M5）。
   - 任务栏歌词：**保持实时刷新**，不影响你在任务栏看歌词。
   - 后端播放/位置上报：保持不变（任务栏歌词依赖它）。
   - 后端 FFT 计算：仍按播放状态运行（任务栏歌词窗口需要），
     但主窗口侧不再消费。

  也就是说：最小化后省下的是主窗口那条 60fps 循环与相关 atom 写入，
  而不是把整个后台静音。

五、预期收益（相对本轮之前）
----------------------------------------------------------------
  内存
   - 长歌单反复滑动：不再无限增长（此前每行永久驻留）。
   - 播放队列：约省 2/3 的歌词副本。
   - 歌词同步后：工作集不再因为全扫索引而涨 100MB。
   - 极端情况（大库 + DevTools + 长时间使用）：比之前少几十 MB。
   - 正常短时使用：变化不明显，因为你的库本来就小。

  CPU
   - 进首页/歌单：少一次全量 IPC，尖峰下降。
   - 暂停播放：少一条 60fps 循环。
   - 最小化：少一条 60fps 循环。
   - 稳定播放：基本不变（背景渲染与歌词动画是主体，属于要保留的效果）。

  坦白说：本轮不会把 200MB 变成 100MB，也不会把十几 % 变成个位数。
  它解决的是"随使用增长"和"后台空转"，并把几个真实的尖峰拿掉。
